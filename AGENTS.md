# Agent guidance: Blitzkampf (Godot)

Godot 4.7 re-implementation of the arena-shooter prototype in `../blitzkampf/` (three.js). That project is a **reference for gameplay and tuning numbers only**, not a structural template: where it worked around three.js limitations (hand-rolled collision, fixed-tick accumulator, procedural meshes, DOM HUD, WebAudio synthesis) this project uses the native Godot approach. Don't port code line by line; ask what the idiomatic Godot way is.

Open work is tracked in `TODO.md`; update it when finishing or adding tasks.

Status: single-player test arena is playable (movement, 3 weapons, targets, pickups, HUD, placeholder SFX). Multiplayer: players connect, spawn, move and can shoot each other, pick up and drop weapons, and see a Tab scoreboard (server-authoritative with client prediction and remote interpolation; see `TODO.md` M5+). Not started: more maps, real art/audio.

## Stack and project settings

- GDScript with static typing; `class_name` on anything referenced from another script. Keep warnings clean.
- Renderer: **GL Compatibility** (keep it; web-export friendly). Physics: **Jolt**. Avoid features Compatibility lacks (e.g. don't rely on `Decal`/SDFGI/volumetrics).
- 60 Hz physics tick with **physics interpolation enabled** (project settings). Gravity is the project setting `physics/3d/default_gravity = 20`, read via `get_gravity()`; never hard-code it.
- Input goes through the **Input Map** (actions in `project.godot`), never raw keycodes. Gameplay code queries input via `GameInput` (`scripts/core/game_input.gd`), which reports nothing while the mouse isn't captured. The mouse is captured on start. Esc opens the **pause menu** (`PauseMenu`, pauses the scene tree, frees the cursor); Esc/Resume captures it again.
- Named physics layers: 1 `world`, 2 `player`, 3 `target`, 4 `pickup`, 5 `prop` (dropped weapon bodies). Bullets hit world+player+target; the player collides with world only; pickup `Area3D`s are on `pickup`.

## Architecture rules

- The only autoload is `GameSettings` (`scripts/core/game_settings.gd`): persisted display options (`user://settings.cfg`), applied at startup. Because autoloads don't exist yet when a `-s` test script compiles, `tools/` scripts must not reference scripts that use `GameSettings` by class type (e.g. type the pause menu as `CanvasLayer`).

- Scenes + nodes + signals: call down, signal up. `WeaponManager` and `Player` expose signals; HUD, `Sfx` and `Main` listen. Nothing reaches up into the HUD.
- Data in `Resource`s and `@export` vars, not constant files or magic numbers. Movement tuning is `MovementSettings` (`resources/player/movement_settings.tres`); weapon stats are `WeaponDefinition`. **Add a weapon = a new `.tres` + model scene, not a code branch.**
- Player movement is a `CharacterBody3D` with Quake-style accel/friction (`QuakeMovement`) feeding `velocity`, then `move_and_slide()`. Floor/slope/wall handling is the engine's job. No RigidBody player.
- **Input is a source, not a call**: gameplay never reads `Input`/`GameInput`. Each `Player` has a `PlayerInput` node; `input.frame()` returns that physics tick's `InputFrame` (move, yaw/pitch, held buttons, edge events), sampled once per tick from an `InputSource` (`LocalInput` = keyboard/mouse via `GameInput`, `ScriptedInput` = tests/bots; the network will add another). `Player` and `WeaponManager` consume frames only. A bot or remote player is a normal `Player` with a different source. Weapons are looked up by id through `WeaponCatalog` (`resources/weapons/catalog.tres`; add new weapons there).
- Mouse look is handled by the source in `PlayerInput._unhandled_input` (never tick-coupled; `input.look_yaw/look_pitch` are live). Yaw/pitch are plain floats on `Player` that follow them each render frame; the `Head` node is `top_level` with interpolation off and is positioned each render frame from `get_global_transform_interpolated()`. Don't parent the camera to the interpolated body or you get look lag/jitter.
- **Viewmodel camera**: the local player's weapons are drawn by a camera of their own, `ViewmodelView` (`scenes/player/viewmodel_view.tscn`, created by `WeaponManager` for the local body only): a full-screen `SubViewportContainer` with a transparent `SubViewport` that shares the world's 3D scene, a `Camera3D` that copies the world camera's pose each frame, and the two weapon holders. Viewmodel meshes are on visual layer 2 (`ViewmodelView.assign_layer`); the world camera's cull mask excludes it and the viewmodel camera draws only it. So the gun never clips into walls and has its own FOV (the world camera's ADS zoom doesn't scale it). Bodies nobody plays get no holders and no viewmodels. The sub-viewport needs its own `msaa_3d` (it does not inherit the project's, so edges would be jagged) and its camera gets a copy of the world's environment with a clear background (`ViewmodelView._copy_environment`): otherwise the world's sky colour sits in the transparent pixels and shows as a light halo around the weapon. Lights are culled by the camera's cull mask too (by the light's own visual layer), so a camera that only draws layer 2 never sees the world's sun (layer 1) and the viewmodel would get only ambient light, i.e. look flat: `ViewmodelView.bind` adds layer 2 to the world's `DirectionalLight3D`s, and there is a soft view-locked `KeyLight` (layer 2) plus a reduced share of the world's ambient (`ViewmodelView.ambient_energy`).
- **Viewmodel scenes (first-person hands)**: `WeaponDefinition.viewmodel` points at a per-weapon scene (`scenes/weapons/<id>_viewmodel.tscn`, root script `WeaponViewmodel`): `Rig` (animated) holding the `Gun` (the weapon's `*_model.tscn`, with `Muzzle`/`Sight`) and `Hands` (`assets/models/viewmodel/hands.glb`, editable children: every finger joint is a node, curl = rotate its joints around local X), an `AnimationPlayer` with `draw`, `fire`, `fire_ads`, `reload` (each starts/ends at the default pose; the reload is stretched to the weapon's `reload_duration`), and an editor-only `PreviewCamera` (frees itself in the game) placed at the player's eye so the camera Preview in the editor shows what the player sees. The scene origin is the grip: the holder places/aims it, so ADS (the `Sight` marker) and the hip pose work unchanged. Akimbo: the left weapon is the same scene mirrored (`scale.x = -1`) with the support hand hidden (`WeaponViewmodel.set_akimbo`). Poses/animations are tuned in the editor (hand-edit nothing in the .tscn). `tools/make_viewmodels.gd` generated the starting scenes and animations from a pose table: don't re-run it after tuning (it overwrites). `tools/make_hands.py` (headless Blender) regenerates the hand model. Without a `viewmodel` a weapon falls back to its bare `model` (recoil by tween). Remote bodies get no holders and no viewmodels.
- Cosmetic motion (recoil, flashes, crosshair gap, eye height, spawner spin/bob) uses `Tween`s, not per-frame damp code. Dropped weapons are real `RigidBody3D`s (keep `continuous_cd` on, or thrown weapons sometimes tunnel through the floor).
- Weapon logic lives in `WeaponManager` (child of `Player`): firing via `intersect_ray`, spread, ammo, reload, pickup, drop. Pickups are `PickupArea`s (spawners and dropped weapons both use one); `pickup_priority` makes dropped weapons win over spawners.
- Sounds are played by name through `Sfx` (`scripts/audio/sfx.gd`); swap sounds by replacing the `.wav` files.
- **Maps** (`MapCatalog`, `resources/maps/catalog.tres`; the first entry is the default; add a map = one `MapDefinition` with either a `scene` or a `map_file`): `Main._load_map` puts the chosen map into the `Map` node *before* any player exists (`Net.map_id` from the menu selector or `--map=<id>`). Maps are authored in **TrenchBroom** as Quake `.map` files in `maps/` (Valve or Standard format) and built **at runtime** by FuncGodot (`FuncGodotMap`, map settings `resources/maps/map_settings.tres`, 32 map units = 1 m; the builder node is named `MapBuilder` so replicated nodes below it have the same path on every peer). Hand-made `.tscn` maps still work (`test_arena`). Entities (`resources/maps/blitzkampf_fgd.tres`, generated by `tools/make_map_resources.gd` because the weapon checkboxes come from the weapon catalog): `worldspawn` and `func_geo`/`func_detail`/`func_illusionary` (static geometry; worldspawn is on the `world` layer), `player_spawn` (a `Marker3D` in group `player_spawn`; `angle` = facing), `weapon_spawner` (the `WeaponSpawner` scene; checkboxes for the offered weapons, none ticked = all, `respawn_delay`; its `_func_godot_apply_properties` turns the bit mask into `offers` via each `WeaponDefinition.map_bit`), `target`, `env_sun` (`MapSun`, a `DirectionalLight3D`) and `env_world` (`MapEnvironment`, sky/ambient colours; one per map). New entity = a definition in `tools/make_map_resources.gd` (+ a script/scene with `_func_godot_apply_properties(properties)` if it needs properties), rerun it, then `tools/export_trenchbroom.gd`. **Add a weapon** now also means a unique `map_bit` (0-23, never change it once maps use it) on its `.tres`, then rerun `tools/make_map_resources.gd` and `tools/export_trenchbroom.gd`. Textures: PNGs under `textures/` (use `prototype/<name>` in TrenchBroom; `clip`, `skip`, `origin` are the special ones); `tools/make_textures.gd` makes the prototype set. `maps/test_arena.map` was generated from the arena scene by `tools/arena_to_map.gd` (don't rerun it after editing the map in TrenchBroom). The FuncGodot editor plugin is not enabled (the game builds maps without it); enable it if you want the `FuncGodotMap` node's Build button. Exported games need `*.map` (and the textures) in the export filter.
- **TrenchBroom setup (once per machine)**: install TrenchBroom (its user folder is `~/.TrenchBroom/`), run `godot --headless --path . -s res://tools/export_trenchbroom.gd`: it writes the game config into the repo (`trenchbroom/Blitzkampf/`, generated but committed, ignored by Godot through `.gdignore`) and links `~/.TrenchBroom/games/Blitzkampf` to it (pass another games folder as an argument; rerun after changing entities). Restart TrenchBroom, open Preferences > Games > Blitzkampf and set the game path to this project's folder (the script prints it), then File > New Map > Blitzkampf, save into `maps/` and add a `MapDefinition` to the catalog.

## Multiplayer

- **Server-authoritative on Godot's high-level multiplayer (ENet)**. Roles: single player (offline peer, same code path), `--host` (listen server, plays too), `--server` (dedicated, headless), `--join=<address>`. `Net` (autoload, `scripts/net/net.gd`) owns the peer, role, CLI parsing (after `--`: `--host`, `--server`, `--join=`, `--port=`, `--map=`, `--scenario=`) and the join handshake with a protocol-version check (`Net.protocol_version`, bump it when the network protocol changes). The server decides the map: after the version check it sends `_welcome(map_id)`; the client's `Main` builds that map, answers `Net.map_loaded()`, and only then does the server emit `player_joined` (spawn the player) and `Main._on_peer_joined` starts replicating the map's `WeaponSpawner`s to that peer (`WeaponSpawner.show_to`: their `Sync` is not public), so replicated nodes never arrive before the map exists. The entry scene is `scenes/ui/main_menu.tscn`; a CLI role skips it. `Main` calls `Net.start()` and spawns one `Player` per peer with a `MultiplayerSpawner` (`_spawn_player`, node name = peer id).
- **Authority split**: the `Player` body (and its `WeaponManager`) is simulated only on the server (`is_multiplayer_authority()` guards in `_physics_process`); clients show replicated state (the per-tick `snapshot` by RPC, see Prediction below; `StateSync` MultiplayerSynchronizer on change: health, alive, score, held weapons; setters react on clients). Input travels client to server as `InputFrame` packets (`NetInput` sends on the owning client every tick, `RemoteInput` serves them on the server; edge events are running counters so a lost packet loses nothing). `Player.is_local` marks the body this machine's human plays: it gets the camera, HUD and viewmodels; others get the `Visual` character model (`CharacterModel`).
- Never reference the `Net` autoload from scripts that `tools/` scripts type (`Player`, `WeaponManager`, `PlayerInput`...): `-s` scripts compile before autoloads exist. Use Godot's built-in `multiplayer` there.
- **Character model**: `CharacterModel` (`scripts/player/character_model.gd`, the `Visual` node of `player.tscn`) wraps Quaternius' CC0 Universal Animation Library mannequin (`assets/models/characters/ual/UAL1_Standard.glb`, no root motion) and builds its `AnimationTree` in code: a state machine (stand / crouch / air / dead; stand and crouch are 1D blend spaces by speed: Idle, Walk, Jog_Fwd, Sprint; Crouch_Idle, Crouch_Fwd) overlaid on the upper body (`UPPER_BODY` bones) by an aim pose blended by look pitch (Pistol_Aim_Down/Neutral/Up). `Player._process` calls `update(speed, crouched, grounded, alive, pitch)`; remote bodies get speed/velocity/on-floor from the interpolated snapshot. The library only has forward locomotion (no strafing/backwards) and one-handed pistol poses, so strafing looks like running sideways and shotguns are held pistol-style for now. Held weapons are the replicated `Player.held_primary/held_secondary` ids (set by `WeaponManager`), attached to `hand_r`/`hand_l` through grips calibrated from the aim pose (`_calibrate_grips`, `GRIP_OFFSETS`). Swapping the mesh for another character on the same skeleton (e.g. Quaternius Universal Base Characters) needs no code change. `godot --path . -s res://tools/character_preview.gd -- <dir> [pose...]` renders poses to PNGs (needs a display). The local player hides its own model; the collision capsule is still the hitbox.
- **Weapons online**: `WeaponManager` logic runs on the server only. The owning client holds a mirror fed by `_rpc_*` methods (weapon, ammo, reloading, aiming, spread, fired, hit/pickup events; requested in full when the player node appears, since earlier updates would hit a missing node) and re-emits the usual signals, so HUD/viewmodel/Sfx are unchanged. Every peer gets `_rpc_shot` (tracer + impact); other players' sounds are positional: `WeaponManager.heard` (shots via `_rpc_shot`, reloads and pickups via `_announce`) and `Player.jumped/stepped` (re-emitted on clients from `_rpc_sound`) feed `Sfx.play_at` through `Main._hear_player`. Dropped weapons are created through the `DropSpawner` (`MultiplayerSpawner`, group `drop_spawner`, spawn function `WeaponManager.spawn_dropped`; data carries the weapon id, ammo and throw velocities); clients freeze them and show the replicated transform. `WeaponSpawner` replicates `offer_index`/`stocked`; `Target` flashes via RPC. Score (`Player.kills/deaths`) replicates for the `Scoreboard` (hold Tab). Bump `Net.protocol_version` when RPCs or replicated properties change.
- **Prediction and interpolation**: the server publishes one `Player.snapshot` per tick (ack sequence, position, velocity, yaw, pitch, stance, slide time, physics tick). Clients tag every `InputFrame` with a sequence number (`PlayerInput`); `RemoteInput` queues packets and consumes one per server tick in order, so the server sees the frames the client predicted from, and acks the last one. Every packet carries the previous frame too (one lost packet costs nothing). If the queue is empty the player's frame is `idle` and the body does not move that tick (repeating the last input would give the server a step the client never took); a backlog beyond `CATCH_UP_QUEUE` is drained by simulating a second frame in the same tick (`InputSource.extra_frame`). The human's own client runs `Player._simulate` itself (`predicting = is_local and not authority`), keeps a history of `[sequence, frame, position]`, and `_reconcile`s when a snapshot's ack differs from its prediction by more than 2 cm: rewind to the server state, replay the unacknowledged frames (`_replaying` suppresses sounds), and fade the visual difference out via `_error_offset`; beyond 2 m it snaps (respawn, first snapshot). Other players are drawn 100 ms in the past by blending buffered snapshots. The server sends `snapshot` itself, once per physics tick, by unreliable-ordered RPC (`_rpc_snapshot`) to the peers that announced their copy of the player (`_rpc_want_snapshots`, sent from the client's `_ready`); it is deliberately not a `MultiplayerSynchronizer` property, which would send on every rendered frame (a headless server renders far faster than 60 Hz) and make remote players move in little jumps. `_receive_snapshot` still drops duplicate or old ticks and stamps each snapshot by its tick number, not its arrival time (`_steady_ms`: a clock offset that follows the earliest arrivals) (scenario `remote_smooth`). Weapon *feedback* is predicted on the human's client (`WeaponManager._predict_feedback`: ADS pose/FOV, recoil, shot sound, tracer/impact, spread and the magazine count start at once; the server's `_rpc_aiming`/`_rpc_fired`/`_rpc_spread`/`_rpc_shot` are ignored there). The spread roll is seeded by the frame's sequence number and hand, so the predicted shot takes the server's path. Each slot counts `shots`; the server sends the count with every ammo update and the client subtracts its still-unconfirmed predicted shots (`pending_shots`, dropped after 1.5 s or when a reload starts) from the displayed magazine. Damage and hit confirmation still resolve on the server (see lag compensation below). `Player` code must stay deterministic given `_frame` plus the snapshot state. Packed arrays and small tuples have named layouts, never bare indices: `Player.Snap` (snapshot floats), `Player.Step`/`Pose`/`Blend`/`Queued` (history and buffer entries), `RemoteInput.Field`/`Count` (input packet and press counters). Extend the enum, not a literal number, when adding a field.
- **Lag compensation**: each snapshot carries the server's physics tick, and the server keeps ~60 ticks of every body's pose (`Player._pose_history`, `pose_at`). The predicting client estimates `Player.view_tick()` (the server tick it is drawing other players at: newest snapshot tick plus time since it was due, minus the 100 ms interpolation delay) and `NetInput` sends it in each `InputFrame`. For a shot from a remote human, `WeaponManager._cast_ray` tests the world and targets with the physics ray, but players with `CapsuleRay` (ray vs capsule maths) at their pose at `view_tick`, rewound at most `Player.MAX_REWIND_TICKS` (30). It's maths, not moving bodies, because Jolt queries don't see mid-tick node moves. Host, bots and single player have `view_tick` 0 and shoot at the present. Known limit: a victim can be hit slightly after running behind cover (the usual trade-off). Scenario `lagcomp` (80 ms client hits a 6 m/s strafing bot 17/17; 1/17 without rewinding).
- **Simulated lag**: `--net-lag=<ms>` (each way, applied by the client) and `--net-loss=<percent>` on a client (`NetSim`, no root needed); the `prediction` net scenario uses them. `tc netem` still works for real packet-level tests.
- **Debug console (F1)**: `DebugConsole` UI sends a line to `Main.submit_command`, which runs it on the server through `DebugCommands` (help, players, weapons, give, ammo, damage, heal, kill, respawn, tp, bot, botclear, botmode; targets are `me`, a peer id, `botN` or `all`) and sends the text back. The host and single player always may use it; remote clients only if the server runs with `--cheats`. Add a command with a `_HELP` entry and a `_cmd_*` method in `scripts/debug/debug_commands.gd`.
- **Bots**: `Main.spawn_bot()` spawns a normal `Player` with `is_bot = true`, a made-up peer id above `Player.BOT_ID_BASE`, and a `BotInput` source (`scripts/player/bot_input.gd`: wanders, avoids walls, shoots the nearest visible enemy with aim error; stands still and holds fire at random so testers get quiet moments, `botmode auto|idle|wander|fight` overrides; no navmesh yet). They exist only through the server and replicate like any other player.
- Pause behaviour online is "mouse released, game keeps running".

## Gameplay decisions carried over (don't relitigate)

- Sprint is just a higher speed cap, no stamina. Walk 7, sprint 11, crouch 3.5 m/s. Jump 7. Holding jump re-jumps on landing.
- Grounded with no input stops instantly; friction applies while steering. Air accel 30, air speed cap 7.
- **Ledge climb (mantle)**: airborne, steering toward a wall, you climb a ledge when the top is at least `mantle_min_height` above the feet and at most `(1 - mantle_body_above) * standing_height` (default: 2/3 of the body above it), and the standing capsule fits on top (`Player._find_ledge`: wall ray at hand height, ray down for the top, shape query for room). Walking into a ledge on the ground does nothing: you jump. The climb is a movement state (`Player.Mantle`: rising, then forward over the lip; no gravity or steering; crouch lets go; getting stuck aborts it) with the target, phase and approach speed in the snapshot. It is eased by acceleration limits, not a fixed-speed path: the rise speeds up from the jump's vertical speed and slows near the lip, the carry over the lip starts slightly below it so the two blend, and the approach speed is kept (`mantle_momentum`), so it is predicted and reconciled like slides. All numbers are in `MovementSettings` ("Ledge climb"). Animation/sound still to do.
- Crouch is a held stance (Ctrl). A fresh crouch press while sprinting + grounded + moving starts a **slide**: entry speed at least 11, momentum-locked (friction only, no steering), speed held flat for 0.15 s then decays, ends on crouch release, leaving the ground, or dropping to crouch speed. You only stand up if there is headroom (`ShapeCast3D`).
- **Aiming down sights** (hold RMB, cancelled by reloading): `WeaponManager` tweens the weapon holder so the model's `Sight` marker sits on the camera axis `ads_sight_distance` in front of the camera, and zooms to the weapon's `ads_fov` over `ads_time`; releasing returns to the hip pose captured from `player.tscn`. All three are `WeaponDefinition` fields. Recoil moves the model node itself, not the holder, so it never fights the aim tween.
- **Akimbo**: `WeaponManager` has two `WeaponSlot`s, primary (right hand, `WeaponHolder`) and secondary (left, `WeaponHolderLeft`). `WeaponDefinition.one_handed` (pistol, SMG) weapons can be paired; two-handed ones (shotgun) always take the primary slot alone. With two weapons there is **no ADS**: LMB (`fire`) shoots the primary, RMB (`fire_secondary`, same button as `aim`) the secondary. This default mapping may become configurable later (the roles are separate Input Map actions). Each slot has its own ammo, cooldown and spread. R reloads every non-full weapon one after the other, left first (full weapons are skipped, nothing happens if all are full), and nothing can fire while any reload is running or queued; the crosshair shows the widest. Pickup rules: F with a one-handed primary adds/replaces the **secondary**; G replaces the **primary** (and swaps a lone weapon); a one-handed pickup over a two-handed primary replaces it; picking up a two-handed weapon drops everything held. Replaced weapons are dropped with their ammo.
- **Health and damage**: `Player` has `health` (100), `take_damage(amount, attacker)`, signals `health_changed`/`damaged`/`died`/`respawned`. Anything damageable exposes `take_damage(amount, attacker)` (`Target` ignores the amount and just flashes). Damage comes from `WeaponDefinition.damage` per hit. Dying drops everything held, locks controls (body still falls) and respawns after `respawn_delay` (3 s) at a random `player_spawn` marker (`Player.spawn()`, also used for the first spawn) with the starting weapon. The player's capsule on layer 2 is the hitbox bullets test; the shooter's own body is excluded from the ray.
- **Pickup prompt**: the local player's `WeaponManager` polls `_find_pickup()` each tick (same reach test as the pickup itself, on the client's view) and emits `pickup_hint_changed(definition, choice)` on change; the HUD shows it. Pickups themselves are not predicted: the server decides, so the weapon appears after a round trip.
- Weapons fire hitscan, automatic while held, gated by per-weapon cooldown. Ammo is **per weapon instance**: picking up a weapon (F/G, edge-triggered) always drops the weapon it replaces with its remaining ammo, even if it's the same type. Fresh spawner weapons are fully stocked. Reload is R, blocks firing, no auto-reload; empty mag can't fire.
- Spread is a flat set of named per-state fields on `WeaponDefinition` (ADS / hip standing / hip moving, moving = horizontal speed > 0.5 m/s). The crosshair renders the same spread value the shot uses. Add a state by adding a field, not a multiplier system.
- Spawners offer a random weapon from their list and respawn 8 s after pickup. Tracer lasts 0.1 s; impact marks are capped at 60 (oldest recycled) so scatter patterns stay visible.

## Differences from the three.js version (intentional)

- `move_and_slide()` collision instead of an AABB sweep, so there is no bit-exact determinism for client prediction. If multiplayer arrives, rethink prediction against Godot's high-level multiplayer rather than reviving the old shared-kinematics idea.
- Crash/diagnostics logging dropped (browser-only); use Godot's debugger and monitors.
- Weapon models are scenes wrapping imported models (currently Quaternius' CC0 Ultimate Gun Pack: pistol = Pistol_2, SMG = SubmachineGun_4, shotgun = Shotgun_3) instead of procedural meshes. The pack's FBXs are ~10x too big and face +X, so each model scene rotates the model 90 degrees about Y and scales it by 0.12 on its `Model` node. `Muzzle` and `Sight` are children of that `Model` node (positions in the model's native units), so the scale is the only number to change to resize a weapon; you may also want to adjust `ads_sight_distance` and the hip pose in `player.tscn`. To swap a model, change the instance in the `*_model.tscn` so the barrel points along -Z, and reposition its `Muzzle` (tracer origin, barrel tip) and `Sight` (rear-sight top; lines up with screen centre when aiming) markers. Model origin should be near the grip, since the viewmodel holder positions the hand. Pickups and dropped weapons re-centre whatever model they show (`ModelBounds`), and the dropped weapon's collider is sized from the model's bounds.

## Workflow

- Network tests: `godot --headless --path . -s res://tools/net_test.gd [-- scenario ...]` starts a dedicated server (or host) and client processes per scenario in `tools/net_scenarios/` (connect, two_clients, shoot, version_mismatch, host); results and logs land in `user://nettest/`. Add a scenario by subclassing `NetScenario` (`run_server`/`run_client`) and listing it in `net_test.gd`. By hand: `tools/run_local.sh [clients]` opens a host and N client windows (only the focused one gets input).
